Newest first. Versions refer to the analysed WhatsApp Android APK.

## Unreleased
- Message Secrets: `deprecated_lid_session` resolved from "not found/not re-verified in 2.26.41.6" to confirmed absent as of 2.26.45.10 — exhaustive case-insensitive grep across the full decoded 2.26.45.10 tree and WA Business 2.26.45.7 found no exact or near match; the only lookalikes are the unrelated protobuf field `is_syncd_pure_lid_session` and an unrelated Jid-validity reason-code fragment `"deprecated_lid"`. `found`: string absent from both builds. `inferred`: intentional removal of the transitional PN→LID migration flag, not a rename.
- New report: `WA_HATCH_MUSE.md` — the Hatch/Muse AI agent subsystem (agent-browser VM + workspace), never previously documented in this repo. Covers the attested Noise-gateway transport (`/v1/noise` over Tigon, native `libwa-noise-gateway-carrier-jni.so`, AMD SEV-SNP attestation variants incl. chip-pinning), the `hatch-api.meta.ai` control plane and WAFFLE-gated onboarding, the agent-browser noVNC screen stream (JWT-bearer-authenticated WebSocket), the workspace features riding the same transport (spaces, feed, goals, ideas, artifacts, approvals, connectors, scheduled tasks, workspace filesystem, identity docs) and the server-side secure-credential store. Corrects an earlier "virtual-card vault" mislabel: `hatch/cvm` is the agent's own CVM identity/chip-attestation recovery system (PIN-as-password OPAQUE PAKE + post-quantum wrapping against `libvesta_client_jni.so`, round-tripped to `hatch-api.meta.ai/hatch/vesta-auth/*` over plain HTTPS, not the attested VM channel) — a cryptographic blocker, not an attested-transport one. Also documents the paid subscription tier (`ai_hatch_in_app_subscriptions_enabled`, `NME_SUBSCRIPTION`, `HatchGenFrlPaymentsAccessTokenMutation`). Honest verdict: almost the entire subsystem needs the native Noise carrier plus WAFFLE attestation or native OPAQUE/PQ math; the only client-reachable surface is four name-based MEX reminder ops (`GetMetaAiReminders`/`DeleteMetaAiReminder`, `GetMetaAiGroupReminders`/`DeleteMetaAiGroupReminder`) and the subscription-compliance/payments-token GraphQL ops — JS-impossible for velowa otherwise.
- Meta AI: new §7.1 (2.26.45.10) — Private Search ships as one more bot-chat thread kind (`PrivateSearchThreadsManager` extends the same `BotThreadsManager` base as `IncognitoAiThreadsManager`, enum `UNKNOWN`/`DEFAULT`/`INCOGNITO`/`SIDE_CHAT`/`PRIVATE_SEARCH`), with the query sent via the same generic message-creation/outgoing-queue path already documented for bot messages — no GraphQL/MEX/IQ call in this path. Corrects the prior "fully native/unreachable" framing: the search-initiation send is reachable like any Meta AI chat send, but the actual PSI/TEE retrieval (`libpsi.so`, native, cross-referenced to the Labyrinth/TEE research) stays unreachable — a reachable-send/unreachable-value split, not a flat "unreachable".
- New report: `WA_ORG_ACCOUNTS.md` (APK 2.26.45.10) — org-account membership model (`org_id`, member directory, team/member-tag taxonomy), the full invite-link join flow (`OrgInvitePreview` -> `OrgCheckDisplayName` -> `OrgCheckEmailEligibility` -> `OrgSendEmailCode`/`OrgVerifyEmailCode` -> `OrgJoin` -> `OrgDirectory`/`OrgMemberSearch`/`OrgLeaveMutation`), 9 `GraphQlOrgApi`/`OrgEmailCodeClient` ops across `www`/`mex` with recovered call-site variables, and the org account vs. Managed Account vs. Business API/Cloud-API delegation distinction (three separate, non-overlapping account-structure concepts). Response shapes for all 9 ops are unknown; `OrgList`'s variables and the full `relationship` enum remain unresolved.
- Username: new §9a (2.26.45.10) — phone-number-sharing audience controls (`com.whatsapp.pnsharing`), separate from the username's own visibility rules in §9. `UsernamePhoneNumberPrivacyUpdateMutation` is incremental, not full-replace: a top-level `setting` (`ALL`/`MYCONTACTS`/`MYCONTACTSEXCEPT`/`NONE`) plus per-list `entries[]` of `{entry_type: USER|GROUP, operation: ADD|DEL, group_jid|pn_jid|user_jid}`, with a `dhash` field for cache validation. Read side is a new batched `UsernamePhoneNumberPrivacyGetQuery` fetching all 3 audience lists at once. A related doc_id, `PnSharingPhoneNumberFetch`, exists in the persisted-query catalog with no call site anywhere in the decoded build — left as unresolved/unknown, not guessed at.
- Polls: new §8.1 (2.26.45.10) — a new `PollEditActivity` ("edit poll") lets a sender rename or add/remove options on an already-sent poll; option removal is a client-side staged rollout (`LX/Ihb;->getPollRemoveOptionRollout()`) with no dedicated flag on the diffed option list. The 2.26.41.6→2.26.45.10 proto diff shows zero poll-related wire changes. Left open as genuinely unknown: adding an option is inferred to reuse `pollAddOptionMessage` (field 121); rename/removal have no confirmed wire primitive (candidates: `Message.editedMessage` full-poll replacement, or reuse of `pollUpdateMessage`'s encrypted `vote` field) — the save button's network call sits behind an R8-merged `LX/A50` click dispatcher that could not be isolated from smali alone.
- Media Upload: new §14.1 (2.26.45.10) — per-chat theme/wallpaper "send to chat" (`ChatThemeViewModel.sendThemeToChat` → `ChatThemeSettingSenderImpl.A06`/`A01` → `ChatWallpaperUploader.A00`) reuses the generic `MediaUploadCoordinatorImpl` E2EE media pipeline unmodified: the wallpaper is re-encoded, copied to local storage, uploaded via AES-256-CBC+HMAC, and the result copied into the same generic `LX/1iA` media-attachment setter surface ordinary `imageMessage` builders use. Sent to a real chat peer, not local-only. Unresolved: the exact `Message` oneof field hosting the attachment, and whether solid-color (no-wallpaper) themes are sent at all.
- New report: `WA_GROUPS_AND_COMMUNITIES.md` — group vs. community structural model (parent/linked/default sub-group, general chat, `C23201A1a.A01` classification pulled together from `WA_GROUP_HISTORY.md` §2.3), legacy `w:g2`/`w:gp2` wire surface, the full group (21 ops) and community (4 ops) `whatsapp-android-mex` operation catalog with recovered call-site variables, invite-link and `groupInviteMessage` wire form, `SetGroupProperty` admin-settings field table, and community join approval (2.26.45.10): the new `CommunityJoinApprovalNuxBottomSheet` passes the community's own `group_jid` into the pre-existing `GroupFetchAllMembershipApprovalRequestsJob`, confirming with code that a community rides groups' `QueryMembershipApprovalRequests`/`GroupMembershipRequestUpdate` MEX pair (with a legacy `w:g2` `membership_approval_requests` IQ fallback) rather than having a distinct community-approval surface; the new `JoinMembershipForm` op is flagged as the inferred submit-side candidate, not confirmed.
- Ban System: new §7.3a (2.26.45.10) — the login-failure ban-appeal flow (`BanAppealActivity`) now prewarms a Google Play Integrity attestation token as soon as the appeal screen opens (`BanAppealPlayIntegrityPrewarmer`/`BanAppealSignalsAggregator`/`BanAppealExistRequester`), before `appeal_token`/`backup_token` go out with the `ban_appeal` request. Raises the automation bar on appeals; does not change the appeal states themselves.
- Call Links: new §15.1 — a live guest client (velowa) joined a real call link end to end, repeatedly, resolving several things the browser captures alone could not show: `guest_reg`'s response body (`{ent_access_token, ent_canonical_fbid, lid, status:"ok"}` — the guest's `lid` is assigned at registration, not only at admission), that the login `ClientPayload` needs `username` set to that `lid`'s number (without it the Noise handshake completes but the server drops the connection right after), and — resolving §10/§16's open question — that a guest's `enc_rekey` is a real, Signal-decryptable call key: it installs into the media engine and the relay/media connection comes up with it, the same as for any other participant. Also confirms a clean leave (`terminate` + `group_call_duration`) shows as `state="terminated"` in the host's roster, not a drop.
- Call Links: §15 extended with source-level confirmation (second guest session, 106 executed scripts dumped via `Debugger.getScriptSource`) — the literal guest `ClientPayload` builder (`accountType = GUEST`, `product = WHATSAPP_LID`), and the module chain proving the guest path is a thin bootstrap/bridge layer (`WAWebGuestCoreBackendBootstrap`/`WAWebGuestCallingVoipBridge`) in front of the same `WAComms`→`WANoiseHandshake`→`WAFrameSocket` stack and `WAWebHandleVoipCall` signalling a normal client uses, not a parallel implementation.
- Call Links: new sections 14-15 on guest registration — a browser guest registers via `v.whatsapp.net/v2/guest_reg` (same Signal identity bundle shape as normal registration, plus `guest_type`/`invite_code`/`guest_name`) and logs in over the ordinary Noise XX transport with `ClientPayload.accountType = GUEST` (field already defined in the shared proto, found unwritten on Android in WA_NOISE_TRANSPORT.md).

- Meta AI: new section "Bot Signature Verification" in `WA_META_AI.md` — live-tested (not static-only) finding. The EdDSA + X.509 signature on `richResponseMessage` (chain roots to Meta's own CA, private key never leaves Meta's backend) binds to *(content, phone number)*, not to live sender identity. A captured, genuine proof replayed from a non-bot sender to the matching number still renders as verified AI content (at most a one-tap "unknown sender" consent gate, not a hard block).
- New reports (APK 2.26.41.6): `WA_INTEROP.md`, `WA_CENSORSHIP_CIRCUMVENTION.md`, `WA_SERVER_DRIVEN_UI.md`, `WA_ACCOUNT_LESS_SURFACE.md`.
