# WhatsApp Call Links — Full RE Report
**Версия:** 2.26.41.6 | **Дата:** 2026-11-02
**Область:** Гостевые ссылки на звонки (`call.whatsapp.com/{voice|video}/{token}`): рукопожатие `link_query` / `link_join`, зал ожидания, модель гостевого участника / выделения JID, а также relay и ключевой материал, передаваемые гостю при допуске. Этот отчёт охватывает только уровень ссылки/зала ожидания/гостя; общая грамматика конверта `<call>`, offer/accept/terminate, ключ звонка, логика выбора relay и медиапуть описаны в [WA_CALL_SIGNALING.md](WA_CALL_SIGNALING.md) и здесь только упоминаются, а не повторяются.

---

## 1. Что это

Call link — это токен, позволяющий участнику присоединиться к звонку без приглашения по JID. Сервер разрешает токен в работающий или запускаемый звонок и, если у звонка включён зал ожидания, держит присоединяющегося там до допуска. Всё в разделе 3 и далее, ниже таблиц со структурой станз, относится к тиру **tested**: прочитано из реального перехвата трафика при присоединении клиента к собственному тестовому call link, расшифровано и декодировано самим присоединяющимся клиентом (а не перехватом трафика третьей стороны). Статика APK (тир **found**) подтверждает те части, которые перехват не показывает, в первую очередь создание ссылки. Логика на стороне сервера относится к тиру **unknown**, если не указано иное.

| Сущность | Форма | Задаётся кем | Тир |
|--------|------|--------|------|
| URL ссылки | `https://call.whatsapp.com/{voice\|video}/{token}` | клиент формирует шаблон вокруг токена | found |
| Токен | 22 символа, смешанный регистр, буквенно-цифровой (`Voip.kCallLinkTokenLength`=22) | в точке создания в Java нет параметра токена; серверное назначение — рабочее предположение | found (длина), inferred (происхождение) |
| Call-id | 32 hex-символа (16 байт), например `0076804DB4CA9D41EFCB547F08AE87BD` | сервер, возвращается в подтверждении `link_join` | tested |
| `is_guest_eligible` | bool на ссылке | хост выбирает при создании (`CallLinkInfo.isGuestEligible`) | found (поле), tested (значение на проводе) |
| `waiting_room` `enabled` | bool на ссылке | хост выбирает при создании (`Voip.createCallLink(..., waitingRoomEnabled)`) | found (поле), tested (значение на проводе) |
| Гостевой участник | запись в ростере с `account_kind="guest"` и JID, выделенным сервером | сервер, при допуске | tested |
| JID домена call | голый домен `call` до появления call-id, `<call-id>@call` после | сервер | tested |

## 2. Доказательная база

Были захвачены два независимых гостевых присоединения от начала до конца, оба с уже аутентифицированного соединения chatd (у присоединяющейся сессии есть собственная identity на проводе), которая намеренно использует путь ссылки с самостоятельно выбранным display name и без раскрытия identity, а не присоединяется как собственный JID аккаунта:

| | Видео-ссылка | Только аудио-ссылка |
|---|---|---|
| Токен | `7vEdtKy61dqCtbWAQ59zuO` | `ENcQnTAwKj7lQOdOHVJPmQ` |
| Call-id | `0076804DB4CA9D41EFCB547F08AE87BD` | `00BC509C0194CE83E26FA85A0319FD9C` |
| Создатель звонка (хост) | `48615137533978` устройство 24 | `21428363591910` устройство 0 |
| Отправленный push_name гостя | `Baron als Gast ohne wa` | `Baron aus web testt` |

Обе сессии адресуют хоста и создателя этого call-id с формой JID `type=1, domainType=1` без явного атрибута `server`; в тех же перехватах та же форма для того же самого аккаунта в других местах сопровождается явным `server="lid"` (например, в подтверждениях получения класса message). В совокупности это читается так: сигналинг звонков здесь работает через LID-identity, что согласуется с примечанием в WA_CALL_SIGNALING.md §3.2 о том, что станзы звонков допускают LID в `to` при ином домене у `call-creator`.

Чего этот перехват не показывает: по-настоящему безаккаунтную браузерную сессию (без предварительного входа в WhatsApp вообще), обращающуюся к той же ссылке. Приведённые ниже формы станз — это протокол уровня сигналинга звонков для гостевого присоединения; дают ли клиенты по-настоящему анонимного веб-посетителя байт-идентичные станзы или проходят через дополнительный шаг провижининга первым — относится к тиру **unknown**.

Клиентское ограничение частоты на создание ссылок не найдено.

## 4. Query и join (tested)

### 4.1 `link_query`

Отправляется пустым, до того как известен какой-либо call-id, на JID домена call без пользовательской части (`to: {user: null, server: "call"}`):

```
<call to="@call" id="...">
  <link_query token="7vEdtKy61dqCtbWAQ59zuO" media="video"/>
</call>
```

Подтверждение:

```
<ack from="@call" class="call" type="link_query" id="...">
  <link_query link_creator="<host jid>" media="video" token="...">
    <guest is_guest_eligible="1"/>
    <waiting_room enabled="1"/>
  </link_query>
</ack>
```

`link_creator` указывает хоста; `is_guest_eligible` и `waiting_room enabled` — это настройки ссылки на момент создания (§3), отражённые обратно. Call-id пока нет — это подтверждение лишь предпросматривает ссылку.

### 4.2 `link_join`

Несёт тот же `token`/`media`, плюс выбранный `push_name` и обычные медиа-дочерние элементы в форме offer:

```
<call to="@call" id="...">
  <link_join token="7vEdtKy61dqCtbWAQ59zuO" media="video" push_name="Baron als Gast ohne wa">
    <audio enc="opus" rate="16000"/>
    <video dec="H264" device_orientation="0"/>
    <net medium="2"/>
    <capability ver="1">...7 bytes...</capability>
  </link_join>
</call>
```

`link_join` ссылки только с аудио (второй перехват) полностью пропускает дочерний элемент `<video>` — подтверждено прямым сравнением, а не выведено:

```
<link_join token="ENcQnTAwKj7lQOdOHVJPmQ" media="audio" push_name="Baron aus web testt">
  <audio enc="opus" rate="16000"/>
  <net medium="2"/>
  <capability ver="1">...</capability>
</link_join>
```

`push_name` — это произвольный текст, который гость выбирает для этого присоединения; это не собственное display name аккаунта в WhatsApp (присоединяющийся аккаунт в обоих перехватах — реальная вошедшая в систему сессия, но выбранное имя отличается от её обычного имени профиля — гостевая identity на этом этапе существует только для отображения). Наблюдаемые 7 байт `<capability>` (`01 05 F5 09 E0 BB 53` видео-гость, `01 05 F7 09 E0 3B 53` хост) — это значения, специфичные для сессии, а не общая маска; WA_CALL_SIGNALING.md §5.2 уже отмечает значения байта capability Android как unknown в общем случае, и это их не раскрывает.

Подтверждение на `link_join` теперь несёт call-id — сервер разрешил (или запустил) звонок:

```
<ack from="@call" class="call" type="link_join" id="...">
  <waiting_room link-token="7vEdtKy61dqCtbWAQ59zuO" media="video"
                call-id="0076804DB4CA9D41EFCB547F08AE87BD"
                call-creator="<host jid>" enabled="1"/>
  <guest is_guest_eligible="1"/>
</ack>
```

### 4.3 Адресация JID домена call (tested)

Это раскрывает часть WA_CALL_SIGNALING.md §10.1, где тип JID домена call оставался неопределённым:

1. `link_query` / `link_join` адресуются к голому домену `call` — без пользовательской части (`callDomainJID`).
2. В момент, когда подтверждение `link_join` возвращает `call-id`, клиент начинает адресовать последующие станзы внутри звонка (heartbeat зала ожидания, а позже mute/transport/relaylatency/video) на `<call-id>@call` — JID с пользовательской частью под тем же доменом (`callJID`).
3. Собственный push допуска сервера (§5) впоследствии приходит `from="<call-id>@call"`, подтверждая ту же адресацию на входящей стороне.

Таким образом, call-id, как только он становится известен, *является* пользовательской частью JID для всего последующего — а не отдельным ключом корреляции, передаваемым наряду с адресацией.

## 5. Зал ожидания (tested)

Во время ожидания присоединившийся, но не допущенный гость отправляет периодический heartbeat на JID call-id:

```
<call to="<call-id>@call" id="...">
  <heartbeat call-id="0076804DB4CA9D41EFCB547F08AE87BD" call-creator="<host jid>" type="waiting_room"/>
</call>
```
подтверждается немедленно (`<ack ... type="heartbeat"/>`, без содержимого).

**Оговорка о допуске**: этот перехват односторонний — он показывает только собственное соединение гостя. Действие на стороне хоста, допускающее ожидающего гостя (`waitingRoomAdmit`, отправка станзы `waiting_room_toggle`/`_admit`, по WA_CALL_SIGNALING.md §10.3), выполняется на соединении *хоста* и здесь не наблюдалось; этот отчёт показывает только его результат. В обоих перехватах допуск (§6) следовал за единственным видимым heartbeat значительно меньше, чем за секунду — достаточно быстро, чтобы оставалось **unknown**, отражает ли это бдительного хоста, немедленно нажавшего Admit, или некое условие авто-допуска (например, хост уже активен в звонке); никаких данных здесь, различающих эти два варианта, нет.

## 6. Выделение JID гостя (tested)

Допуск приходит как обычный push `group_update`/`group_info` от `<call-id>@call`, с двумя записями `<user>` — хост и гость рядом друг с другом:

| Поле | Запись хоста | Запись гостя |
|-------|-----------|--------------|
| `jid` | `48615137533978` (устройство 24 под `<device>`) | `29554559176938` (устройство 0) |
| `type` | `admin` | *(отсутствует — нет повышенной роли)* |
| `account_kind` | *(отсутствует)* | `guest` |
| `push_name` | *(отсутствует в этой записи)* | `Baron als Gast ohne wa` — имя, отправленное в `link_join` §4.2, скопированное дословно в ростер |
| `state` | `connected` | `connected` |
| `platform` устройства | `web` | `web` |
| `pid` устройства | `0` | `1` |

JID гостя (`29554559176938`) относится к тому же классу формы адреса (`type=1`, `domainType=1`, т. е. LID-подобный, §2), что и JID хоста, выделен сервером заново для этого звонка — это не собственная account identity присоединяющейся сессии. `pid` устройства (`1` для гостя) совпадает с `self_pid="1"` блока relay в той же станзе (§7) — per-device participant id ростера и собственный participant id relay — одно и то же число.

**Unknown**: используется ли этот JID гостя повторно при повторных присоединениях к той же ссылке тем же браузером/сессией, как долго он удерживается и виден ли он хосту, помимо `push_name` и `account_kind`.

## 7. Передача relay и ключа при допуске (tested)

Та же станза допуска несёт блок `<relay>`, соседний с `<group_info>`, дающий гостю всё необходимое для доступа к медиа без дальнейших обменов. Поля соответствуют грамматике из WA_CALL_SIGNALING.md §8.2; этот раздел добавляет конкретные детали на уровне провода, которые тот отчёт оставил открытыми.

| Дочерний элемент | Наблюдаемое количество | Примечания |
|-------|-----------|-------|
| `<token id=N>` | 3 (id 0, 1, 2) | сырой бинарный, по 194 байта каждый |
| `<auth_token id=0>` | 1 | сырой бинарный, 70 байт |
| `<key>` | 1 | 24 байта на проводе — но эти 24 байта сами по себе являются ASCII-текстом строки base64, которая декодируется ещё раз в сырой 16-байтовый ключ |
| `<hbh_key>` | 1 | 40 байт на проводе — та же схема: ASCII-текст base64, декодируется в 30 сырых байт |
| `<te2 relay_id auth_token_id token_id domain_name relay_name c2r_rtt>` | 6 (2 relay: `edgeray-ham3-1.wt.whatsapp.com`/`ham3c01`, `edgeray-ber1-1.wt.whatsapp.com`/`ber1c01`) | `<te>` не присутствует — подтверждает правило "никогда оба", этот звонок использовал `te2` |
| атрибуты relay | `attribute_padding`, `transaction-id`, `self_pid`, `uuid`, `participant_uuid` | `self_pid="1"` связывается с собственным `pid` устройства гостя в `group_info` (§6) |
| `<participant pid jid>` | не присутствует | дочерний элемент отображения participant-id-в-JID из §8.2 в этом перехвате с 2 участниками не наблюдался; неизвестно, появляется ли он только в групповых звонках |

Только `<key>` и `<hbh_key>` несут двойную форму кодирования (бинарный узел, содержащий ASCII-текст base64); `<token>` и `<auth_token>` — чистый сырой бинарный. Что даёт этот двойной слой по сравнению с прямой отправкой сырых байт, относится к тиру **unknown** (вероятно, остаток текстово-ориентированного транспорта внутри, inferred).

Дочерний элемент `<voip_settings uncompressed="1">`, также соседний с `<group_info>`/`<relay>`, несёт JSON-блоб параметров движка (не сжатый в этом перехвате, что согласуется с примечанием WA_CALL_SIGNALING.md §5.2 о том, что сжатые полезные нагрузки отклоняются хотя бы на одном пути). Внутри него, в объекте `fs` (feature-switch): `"guest_calling_logging_enabled": "true"` — единственный гостевой ключ, найденный в остальном обычном документе настроек размером ~32 КБ (`aec`, `bwe`, `decode`, `encode`, `sfu`, `rc`, ... — всё обычная тонкая настройка медиа-движка, не связанная с гостевым присоединением). Телеметрические события, отправляемые присоединяющимся клиентом вокруг этого звонка, независимо используют строку категории `guest_calling` (видна в собственных блобах `w:stats`/WAM клиента), совпадающую с наименованием ключа настроек.

Два безобидных соседних элемента, `<uploadfieldstat/>` и `<userrate interval="0"/>`, идут вместе в той же станзе; без содержимого, специфичного для гостя.

Клиент немедленно отправляет простой `<ack class="call" type="group_update">` для этого push (без содержимого) — обычная обработка по WA_CALL_SIGNALING.md §3.3 (group_update не входит в набор тегов без немедленного подтверждения).

## 8. Трафик после допуска (tested, кратко)

После допуска трафик неотличим от обычного звонка на том же JID call-id: `mute_v2` (хост немедленно выключает микрофон гостя после допуска в этом перехвате), `transport` (`transport-message-type="4"`, дочерний элемент `<net medium="2" protocol="0"/>`), `relaylatency` (в обоих направлениях, каждый несёт `<te latency relay_name>`, ссылающийся на имена relay из §7), и изменения состояния `video` (`state="6"`, т. е. `Stopped` по таблице `kVideoState*` из WA_CALL_SIGNALING.md §13, повторяется три раза подряд во время настройки). Ничего из этого не специфично для ссылки; см. WA_CALL_SIGNALING.md §§8, 13 для общей семантики.

## 10. Отличия от обычного 1:1 или группового звонка

| Аспект | Обычный 1:1/групповой звонок (WA_CALL_SIGNALING.md) | Гостевое присоединение по ссылке (этот отчёт) |
|--------|------------------------------------------------|-------------------------------|
| Входная станза | `offer` известному peer/group JID | `link_query`, затем `link_join` на голый домен `call` |
| Ключ звонка | per-device Signal-зашифрованный `Message.call.callKey` в offer | в допуске этого перехвата не наблюдался; гость получает relay/ключевой материал (§7) напрямую, а не ключ звонка, обёрнутый в Signal — согласуется с отсутствием у гостя парной Signal-сессии с хостом |
| Identity звонящего/принимающего | обе стороны известны как JID до начала звонка | реальная identity присоединяющейся стороны не раскрывается в ростере; сервер выделяет новый JID и помечает его `account_kind="guest"` |
| Допуск | нет — offer/accept — единственный гейт | опциональный зал ожидания: `waiting_room enabled`, удержание до (ненаблюдаемого, на стороне хоста) допуска |
| Доставка ростера | `group_info` внутри offer или более позднее обновление | push `group_update`/`group_info` от `<call-id>@call`, объединённый с `<relay>` и `<voip_settings>` в одной станзе |
| Адресация JID | JID peer/группы на всём протяжении | голый домен `call` до появления call-id, затем `<call-id>@call` |

Отсутствующий per-device ключ звонка для гостя (строка 2) — самое значимое отличие, и это тир **tested** только как отсутствие в этом перехвате — не подтверждено как протокольное правило; это также согласуется с примечанием WA_CALL_SIGNALING.md §9.2 о том, что групповые offer не несут per-device ключа, и ключи повторно передаются вне канала (`enc_rekey`). Получает ли гость когда-либо `enc_rekey`, не наблюдалось ни в одном из использованных здесь окон перехвата.

## 11. Случаи ошибок / подводные камни

| Симптом | Причина | Исправление / примечание |
|---------|-------|-----------|
| В подтверждении `link_query` нет `call-id` | ссылка ещё не разрешена в работающий/запускаемый звонок | нормально для простого предпросмотра; call-id приходит только в подтверждении `link_join` |
| Гость застревает после подтверждения `link_join`, обмениваются только heartbeat | включён зал ожидания, и хост ещё не допустил | требуется действие на стороне хоста; не видно из соединения гостя |
| `link_join` несёт дочерний элемент `<video>` для аудио-только ссылки | ошибка клиента — оба перехвата показывают, что этот дочерний элемент должен полностью отсутствовать при `media="audio"` | не включать `<video>` для аудио-только присоединений |
| Собственный JID аккаунта гостя появляется в ростере звонка вместо нового JID гостя | неверный путь присоединения (обычный `offer`/присоединение к группе вместо `link_join`) | использовать `link_query`→`link_join` для получения обработки `account_kind="guest"` |
| Гость не получает ключ звонка, но получает relay/ключевой материал | ожидаемо для этого пути (§10) — гость не получает ключ, обёрнутый в Signal, как обычный принимающий | не считать это ошибкой расшифровки |

## 12. Ключевые различия

| Не путать | С |
|-----------|------|
| **Токен** call link (22 символа, обращён к URL) | **Call-id** (32 hex-символа, обращён к протоколу, появляется только после `link_join`) |
| Голый JID домена `call` (до call-id) | `<call-id>@call` (после call-id) — оба являются "JID домена call" на разных этапах, а не двумя несвязанными адресами |
| `is_guest_eligible` (настройка ссылки: может ли *кто угодно* присоединиться к этой ссылке как гость) | `waiting_room enabled` (настройка ссылки: удерживаются ли гости до допуска) — независимые флаги, оба отражаются в одних и тех же подтверждениях |
| `push_name` гостя в `link_join` (произвольный, выбирается при каждом присоединении) | собственное имя профиля WhatsApp присоединяющегося аккаунта (не то, что оказывается в ростере при гостевом присоединении) |
| Байты `<key>` / `<hbh_key>` на проводе (бинарный узел, содержащий ASCII-текст base64, требуется двойное декодирование) | Байты `<token>` / `<auth_token>` на проводе (чистый сырой бинарный, одно декодирование) |
| Выделение JID гостя (на стороне сервера, при допуске, для каждого звонка) | обычные JID LID/PN (на уровне аккаунта, постоянные) |

## 13. Полный поток (гостевое присоединение, из перехвата)

```
[Guest client]  already has a chatd session (own identity, not used for the call)
     │  <call to="@call"><link_query token media/></call>
     ▼
[WA Server]  resolves the token
     │  ack: link_creator, media, token, <guest is_guest_eligible/>, <waiting_room enabled/>
     ▼
[Guest client]  <call to="@call"><link_join token media push_name><audio/>[<video/>]<net/><capability/></link_join></call>
     ▼
[WA Server]  starts/resolves the call
     │  ack: <waiting_room link-token media call-id call-creator enabled/>, <guest is_guest_eligible/>
     ▼
[Guest client]  learns call-id → addresses it as <call-id>@call from now on
     │  <call to="<call-id>@call"><heartbeat call-id call-creator type="waiting_room"/></call>  (repeats)
     ▼
[Host, out of band — not in this capture]  taps Admit (waiting_room_toggle/_admit)
     ▼
[WA Server]  <call from="<call-id>@call"><group_update><group_info ...>
                 <user host .../><user account_kind="guest" push_name jid=<allocated> .../>
              </group_info>
              <relay token×N auth_token key hbh_key te2×N/>
              <voip_settings uncompressed fs.guest_calling_logging_enabled=true/>
              </group_update></call>
     │  ack: <ack class="call" type="group_update"/>
     ▼
[Both]  ordinary call traffic on <call-id>@call: mute_v2, transport, relaylatency, video state
              (see WA_CALL_SIGNALING.md §§8, 13 for generic semantics)
```
