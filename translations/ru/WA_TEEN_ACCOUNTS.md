# WhatsApp Согласие спонсора подросткового аккаунта — Full RE Report
**Версия:** 2.26.45.10 | **Дата:** 2026-11-15
**Область:** пакет `com.whatsapp.vpc.sponsor` — экран рассмотрения для родителя/опекуна ("спонсора") по аккаунту несовершеннолетнего ("подростка") WhatsApp, его модель навигации, проверка возраста на стороне спонсора, три экрана исхода (одобрено/отклонено/невозможно рассмотреть), последствие `account_deletion_time_ms` при отклонении, что достижимо или прослеживается по протоколу, а что нет, и различие от системы родительской супервизии `WA_MANAGED_ACCOUNT.md`

---

## 1. Что это

Новое в `2.26.45.10` (отсутствует в базовой версии `2.26.41.6`): четыре класса в пакете
`com.whatsapp.vpc.sponsor`, реализующие одноразовое решение по рассмотрению, которое принимает
родитель/опекун об аккаунте WhatsApp несовершеннолетнего — одобрить его, отклонить или сообщить о
невозможности его рассмотреть. Структурно это отличается от существующего продукта родительской
супервизии `WA_MANAGED_ACCOUNT.md` (раздел 8 ниже раскрывает это различие); это выглядит как
принятие WhatsApp того же паттерна безопасности подростковых аккаунтов, который Meta уже поставляет
для Instagram и Facebook: опекун должен дать согласие на само наличие аккаунта у несовершеннолетнего,
с последствием удаления аккаунта при отказе.

"VPC" нигде в клиенте не раскрывается; "Verified Parent/guardian Consent" ("подтверждённое согласие
родителя/опекуна") — наиболее вероятная трактовка, учитывая форму функции — **inferred**, не
найденная буквальная расшифровка строки.

| Сущность | Класс | Роль |
|---|---|---|
| Хост-экран | `VpcSponsorActivity` | не экспортируется, нет intent-filter — механизм запуска не разрешён (§6) |
| View model | `X/B18` | хранит обязательные аргументы запуска, выполняет проверку возраста, управляет навигацией |
| Диспетчер навигации/исхода | `X/CaB` | общий класс (также обслуживает не связанные с этим `ConsentFlowActivity` для верификации возраста и `WamoSubActivity`); эта трассировка касается только ветки, обрабатывающей события `VpcSponsorActivity` |
| Исход "Одобрено" | `VpcSponsorApprovedFragment` | показывается при одобрении |
| Исход "Отклонено" | `VpcSponsorDeclinedFragment` | показывается при отклонении; отображает обратный отсчёт до удаления |
| Исход "Невозможно рассмотреть" | `VpcSponsorCannotReviewFragment` | показывается, когда спонсора не удалось верифицировать для рассмотрения |

Все находки — статический анализ декомпилированного APK (декод smali через `apktool`; полный
прогон JADX по APK не выполнялся, согласно практике безопасности этого репозитория для больших
сборок). Ничего из этого не было захвачено по протоколу или выполнено в runtime. Уровни
доказательности: **found** = прочитано непосредственно в smali (строковый литерал, поле или
класс); **inferred** = выведено из структуры кода без буквального именующего литерала; **unknown**
= не разрешено в этом проходе.

Идентичные четыре класса существуют, побайтово неизменные в раскладке полей/строк, в
`com.whatsapp.w4b` (WhatsApp Business) `2.26.45.7` — **found** по наличию класса; повторно не
трассировано независимо, предполагается, что трассировка для потребительской сборки ниже
применима и здесь.

## 2. Модель навигации

Экран управляется закрытым (sealed) типом назначения, `LX/CvW` (найден по наличию класса; сам
интерфейс не несёт самоименующей строки), с семью реализациями, идентифицированными по собственным
литералам `toString()` (found):

| Класс | `toString()` | Что делает |
|---|---|---|
| `X/CSM` | `"AgeCollectionScreen"` | отклоняется в общий кросс-приложенческий поток верификации возраста Meta |
| `X/CSO` | `"ConsentNoticeScreen"` | собственно запрос одобрения/отклонения — **никак не отрисовывается в этом пакете**, см. §4 |
| `X/CSN` | `"ApprovedScreen"` | показывает `VpcSponsorApprovedFragment` |
| `X/CSS` | `"DeclinedScreen(accountDeletionTimeMs=...)"` | показывает `VpcSponsorDeclinedFragment`; несёт метку времени удаления типа `long` |
| `X/CSR` | `"CannotReviewScreen(teenName=...)"` | показывает `VpcSponsorCannotReviewFragment`; несёт отображаемое имя подростка |
| `X/CSP` | `"ErrorExit"` | показывает диалог с тегом `vpc_sponsor_error_exit_dialog`, завершает активность при закрытии |
| `X/CSQ` | `"Exit"` | немедленно завершает активность |

## 3. Обязательные аргументы запуска и проверка возраста спонсора

Конструктор `X/B18` (found) читает три ключа из сохранённого состояния/аргументов навигации
активности, два из них обязательны — отсутствующее значение бросает `IllegalStateException("Required value
was null.")`:

| Ключ | Тип | Примечания |
|---|---|---|
| `vpc_teen_name` | `String` | обязателен; отображаемое имя подростка, позже копируется в bundle экрана "невозможно рассмотреть" как обычный `teen_name` |
| `vpc_account_deletion_time_ms` | упакованное число (`.longValue()`) | обязательно присутствовать, но значение, прочитанное здесь, **отбрасывается** — подтверждено чтением байткода конструктора, локальная переменная никогда не сохраняется в поле. Число, которое экран отклонения фактически показывает, приходит из отдельного поля `X/CSS.A00`, устанавливаемого позже, когда результат рассмотрения производит назначение `DeclinedScreen` |
| `navigation` | допускает null, сравнивается с `X/CSM.A00` | если присутствует и не равно `AgeCollectionScreen`, напрямую задаёт начальное назначение (например, возобновлённый/перезапущенный поток) |

Если начальное назначение не задано, `B18` вызывает
`Lcom/whatsapp/dobverification/ContextualAgeCollectionRepository;->A06()Ljava/lang/Boolean;` —
**допускающий null** булев тип (found):

- **`null`** → перейти к `AgeCollectionScreen`. Общий диспетчер `X/CaB` запускает **экран
  верификации возраста Bloks** для этого состояния — тот же путь кода, который не связанный с этим
  `ConsentFlowActivity` использует для проверок возраста при регистрации (строка лога
  `"ConsentFlowActivity/navigate/launch Bloks age verification screen"`, найдена в общем классе, не
  специфична для vpc, но это та же ветка, в которую попадает состояние `AgeCollectionScreen`
  vpc-sponsor).
- **`true`** → перейти к `ConsentNoticeScreen`.
- **`false`** → перейти к `CannotReviewScreen(teenName)`.

Экран Bloks отвечает через
`VpcSponsorActivity.onAgeCollectionResult(ContextualAgeCollectionUsecaseApi$CACResult)` (found,
точная сигнатура), заново выполняя то же трёхвариантное решение из подтипа `CACResult`, а не из
простого булева значения: результат, несущий булево значение, повторно входит в ветки `true`/`false`
выше; отменённый/блокированный результат направляется в `Exit`; результат отсутствия возраста или
сбоя направляется в `ErrorExit`.

**Интерпретация (inferred, не названная в клиенте):** именно *спонсор* — не подросток — должен
пройти общую кросс-приложенческую проверку верификации возраста Meta, прежде чем ему будет показан
запрос одобрения/отклонения. Спонсор, который не может или не хочет её завершить, никогда не
достигает самого решения о согласии; его направляют в `CannotReviewScreen`, `Exit` или `ErrorExit`
в зависимости от того, как разрешилась проверка возраста.

## 4. Запрос одобрения/отклонения не отрисовывается этим пакетом

Чтение ветки `ConsentNoticeScreen` в `X/CaB` (found, точный байткод): при достижении этого
состояния код повторно проверяет *текущее* значение навигационного `StateFlow` на совпадение с
`ConsentNoticeScreen` ещё раз — и если оно всё ещё совпадает, немедленно перенаправляет в `ErrorExit`
вместо отрисовки чего-либо. Нигде в `com.whatsapp.vpc.sponsor` или в трассируемой ветке `X/CaB` к
этому состоянию не привязан ни фрагмент, ни активность, ни запуск Bloks.

**Вывод (inferred):** реальный UI одобрения/отклонения, с которым взаимодействует спонсор, не
является нативным кодом, достижимым из этого пакета. Наиболее согласованное объяснение, учитывая,
что проверка возраста также управляется Bloks — это серверно-рендеренный экран Bloks, запускаемый
*до* старта `VpcSponsorActivity`, с этой активностью, получающей только **результат** — одобрено,
отклонено или невозможно рассмотреть — для отображения соответствующего терминального фрагмента. В
этом проходе не было найдено ни имени операции GraphQL/MEX, ни идентификатора экрана Bloks для самой
отправки одобрения/отклонения. **Unknown.**

## 5. Терминальные экраны исхода

| Экран | Читает | Показывает | Сетевой вызов внутри самого фрагмента |

| `VpcSponsorDeclinedFragment` | `account_deletion_time_ms` (long, bundle аргументов Fragment, задан из `CSS.A00`) | изображение-заголовок, заголовок, текст тела с временем удаления, **отформатированным как относительная строка/длительность** (через `LX/0Fg;->A05(LX/0Fc;J)Ljava/lang/String;`, не как сырая метка времени), кнопку `"Done"` | не найден |
| `VpcSponsorCannotReviewFragment` | `teen_name` (String, bundle аргументов Fragment, задан из `CSR.A00`) | изображение-заголовок, заголовок с интерполяцией имени подростка, текст тела, кнопку `"OK"`, закрывающую экран | не найден |

**Что `account_deletion_time_ms` означает на практике:** экран отклонения форматирует это значение
через форматтер относительной длительности и показывает его как "оставшееся время", т.е. это
представляется зрителю как **обратный отсчёт**, а не как уведомление о том, что удаление уже
произошло — found, из вызова форматтера. Планирует ли отклонение фактически удаление на стороне
сервера, или удаление уже запущено к моменту отрисовки этого экрана — **unknown**: ни один фрагмент
в этом пакете не делает собственного сетевого вызова; значение просто приходит как аргумент
запуска/навигации, который экран отображает.

Весь текст тела для этих трёх экранов (`str5e24`-`str5e2c` в `res/values/strings.xml` этой сборки)
представляет собой буквальный текст-заполнитель Lorem-ipsum — это бета-сборка; разметка и привязка
данных найдены, финальный отправляемый пользователям текст — **unknown**.

## 6. Точка входа — не разрешена

`VpcSponsorActivity` объявлена как `android:exported="false"` без `<intent-filter>` в манифесте
(found). Поиск по всему репозиторию буквальных ключей аргументов навигации (`vpc_teen_name`,
`vpc_account_deletion_time_ms`) и любой конструкции `VpcSponsorActivity` за пределами её собственных
четырёх классов и общих вспомогательных классов навигации `X/CaB` не возвращает **ни одного
совпадения нигде в декодированном дереве smali** — отрицательный, но найденный результат.

**Inferred:** ничто в этом клиенте статически не строит запускающий `Intent`. Наиболее вероятное
объяснение, согласующееся с тем, как известно работает навигация, управляемая push-уведомлениями, в
других местах этого приложения — это серверно-управляемое действие уведомления, которое разрешает
целевую активность и её extras из данных payload push в runtime, а не захардкоженную точку вызова —
но такой диспетчер не был идентифицирован в этом проходе. **Unknown**, как спонсор фактически
уведомляется и направляется на этот экран.

предполагается идущим через Bloks, а не через именованный persisted-запрос GraphQL/MEX —
согласуется с тем, как работает остальной инструментарий кросс-приложенческой верификации возраста
Meta в этом клиенте — но ни операция, ни идентификатор экрана не были захвачены для чего-либо из

## 8. Ключевые различия

### 8.1 vs. `WA_MANAGED_ACCOUNT.md` ("Managed account")

| `vpc.sponsor` (этот отчёт) | `managedaccount.*` / PAA / PMA / PMTA (`WA_MANAGED_ACCOUNT.md` §2-8) |
|---|---|
| **Одноразовое решение о рассмотрении**: одобрить, отклонить или сообщить о невозможности рассмотреть аккаунт конкретного несовершеннолетнего | **Длящееся отношение супервизии** между двумя независимо зарегистрированными аккаунтами |
| Операция `w:mex` не найдена; предполагается Bloks, идентификатор операции/экрана не захвачен | Девять именованных операций `w:mex` `ManagedAccount*` с doc_id, схема `whatsapp-android-mex` |
| Локальная запись отношения в этом пакете не найдена | Локальная строка `ManagedAccountConnection` (`connectionLid`, `role`, `linkTs`, `connectionPnJid`, ...) |
| Отклонение производит последствие `account_deletion_time_ms` для **самого аккаунта подростка** | Отвязка (`ManagedAccountRevokeLinkingMutation`) завершает супервизию; ни один из аккаунтов не удаляется |
| Нет enum ролей; спонсор — просто "рецензент" | `EnumC08540Ng`: `NONE`/`DEPENDENT`/`SPONSOR`/`SPONSOR_ADMIN` |
| Точка входа не разрешена; активность не экспортирована, нет deep link | Точка входа — внутриприложенческий deep link (`ManagedAccountSponsorOnboardingViewModel`) |
| Не делит ни класса, ни пакета, ни строки с `managedaccount.*`/`pma.*`/`pmta.*` | — |

Ни в одном из пакетов нет кода, ссылающегося на другой по классу или строке. Создаёт или
взаимодействует ли впоследствии одобрение `vpc.sponsor` с отношением `managedaccount.*` — не
трассировано; **unknown**.

### 8.2 vs. обычное создание аккаунта

Обычная регистрация в WhatsApp (`WA_ACCOUNT_LESS_SURFACE.md` / стандартный поток SMS/email OTP)
вообще не имеет шага рассмотрения опекуном; аккаунт становится активным, как только его собственный
владелец завершает регистрацию. `vpc.sponsor` вставляет внешний барьер одобрения — удерживаемый
другим человеком, на другом устройстве — между неким триггером (не разрешён, §6) и продолжающимся
существованием аккаунта, с отклонением, несущим последствие удаления. Что конкретно приводит к
направлению аккаунта в это состояние рассмотрения опекуном в первую очередь (возраст при
регистрации, сигнал возраста на устройстве, более поздняя переклассификация) — не найдено в этом
пакете и **unknown**.

## 9. Примечание о достижимости для Baileys / velowa

Ничто в этом потоке не достижимо для стороннего клиента, работающего только по протоколу. Само
решение одобрения/отклонения предположительно является серверно-рендеренным экраном Bloks,
отрисовываемым собственным первоклассным клиентом спонсора (§4) — не сообщением, IQ или именованной
мутацией GraphQL/MEX, которую velowa мог бы отправить или наблюдать. Проверка возраста на стороне
спонсора (§3) также управляется Bloks. Для какой-либо части этого потока в каталогах этой сборки не
существует ни doc_id, ни имени операции MEX, ни `xmlns` бинарного узла. Здесь нечего реализовывать;
этот раздел существует, чтобы явно зафиксировать это, а не оставлять подразумеваемым.
