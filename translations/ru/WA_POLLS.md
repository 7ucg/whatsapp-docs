# WhatsApp Опросы — Full RE Report
**Версия:** 2.26.41.6 | **Дата:** 2026-11-01
**Область:** семейство сообщений опроса (`pollCreationMessage` до `pollCreationMessageV6`, `pollCreationOptionImageMessage`, `pollAddOptionMessage`, `pollUpdateMessage`, `pollResultSnapshotMessage`/`V3`), история версий и логика выбора при отправке/приёме, валидация и лимиты при создании, связывание вариантов-изображений, выбор голоса и модель приватности, множественный выбор против одиночного, правка опроса, снимок результатов на момент пересылки, флаги функций

---

## 1. Что это такое

Опрос — это вложенный объект `Message` (`PollCreationMessage`, без изменений используется в шести версионированных полях верхнего уровня), несущий вопрос, список вариантов, предел выбора и необязательные настройки викторины/времени окончания/видимости. Голоса (`pollUpdateMessage`), добавленные варианты (`pollAddOptionMessage`) и правки (`secretEncryptedMessage`) — отдельные последующие сообщения, привязанные к id сообщения создания и использующие его посообщённый секрет (per-message secret); это шифрование (use case'ы HKDF, AES-GCM, AAD, повтор идентичности) описано в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) и здесь не повторяется. Этот отчёт охватывает слой типов сообщений: какое поле что несёт, как клиент выбирает между ними, валидацию и лимиты, а также что обработчики, специфичные для опросов, делают с расшифрованными payload'ами. Все находки получены статическим анализом декомпилированного APK 2.26.41.6 (исходники Java в `java_src/`, а также `res/values/strings.xml`); перехвата трафика не производилось. Уровни достоверности: **found** = найдено в коде/ресурсах, **inferred** = выведено из кода, **unknown** = не установлено.

## 3. История версий

### 3.1 Какое поле используется при отправке (found, `F2N.A00`/`A02`)

```text
pollType == QUIZ (correct answer set)              -> pollCreationMessageV5
chat is a community default-subgroup (group_type 3) -> pollCreationMessageV2
else:
  hideParticipantName / endTime / allowAddOption set -> pollCreationMessageV6
  none of those set                                   -> pollCreationMessageV3
```

`pollCreationMessageV4` никогда не заполняется путём отправки, прочитанным в этом анализе; оно появляется только при приёме (§3.3). Проверка на сообщество повторно использует тот же предикат `group_type == 3`, что и запасной вариант с открытой реакцией (plaintext-reaction) в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §6.2 (`C0GQ.A0A(chat) == 3`, устанавливается из `isDefaultSubgroup_`); почему опрос default-подгруппы получает собственный версионированный слот вместо V3/V6, в прочитанном здесь коде не объясняется (inferred: историческая очерёдность развёртывания, так как номер поля V2 самый низкий среди расширенного набора).

Таким образом на практике: **V3** — текущий слот для обычного опроса с множественным/одиночным выбором без дополнений, **V6** — текущий для опроса, использующего время окончания, скрытие имён проголосовавших или добавление вариантов, **V5** — текущий для викторин, а **V2** — специфичный для подгруппы сообщества вариант той же базовой формы. **V1** (неверсионированное поле 49) и **V4** отправителем в этой сборке не выбираются.

### 3.2 `pollCreationMessageV4` = обёртка для прямой совместимости (found, `F2N.CM7`)

Proto-тип V4 — это `FutureProofMessage` (`BD2`, единственное поле `message` = вложенный `Message`). При приёме, если слот V4 заполнен, клиент разворачивает `BD2.message_` и читает поле `pollCreationMessage` (49) *этого* внутреннего сообщения как настоящий `PollCreationMessage`. Это полноценный запасной конверт, а не мёртвое поле: отправитель, которому нужно выдать более новый/неопределённый вариант опроса, может обернуть базовый опрос (в форме поля 49) в V4, чтобы более старые клиенты — понимающие только обычное разворачивание `FutureProofMessage`, а не новый слот — всё равно отрендерили обычный опрос. Ни один путь кода в этом анализе не заполняет V4 при отправке, так что это существует для прямой/обратной совместимости между версиями клиента, а не для чего-либо, что сам клиент 2.26.41.6 отправляет (inferred).

### 3.3 Выбор на стороне приёма и понижение версии (found, приблизительно; декомпилятор потерял часть структуры ветвлений)

`F2N.CM7` проверяет битовые поля `Message` в порядке V1 → V2 → V4 → V5 → V6 → откат к V3 и парсит то версионированное поле, которое заполнено, в тот же валидатор (`F2N.A01`, §4). Три флага контролируют принятие дополнительных полей V6 при приёме; когда флаг выключен, опрос **понижается** (парсится как обычный future-proof заполнитель, а не как пузырь опроса), а не отклоняется полностью:

| Доп. поле | Флаг | Эффект при выключенном флаге |
|-------------|------|--------------------------|
| `endTime` | AB int **24884** (`receivingEnabled`) | в лог пишется `poll downgraded to FMessageFuture (receiving disabled)`, не рендерится как опрос |
| `hideParticipantName` | AB int **24885** | понижение версии (точная полярность проверки не полностью установлена из декомпилированного потока управления) |
| `allowAddOption` | AB int **25758** | понижение версии |

Точную вложенность этих трёх условий не удалось полностью восстановить (JADX сообщает о дублированных/недостижимых блоках в `F2N.CM7`); контролирующие флаги и результат понижения версии — found, точная булева комбинация — inferred.

### 3.4 Флаг для содержимого-изображения

`pollContentType = IMAGE` учитывается только на пути парсинга V3/V5, когда установлен бит для `pollContentType`; если бит установлен, но значение не равно `IMAGE`, сообщение отклоняется (`return null`, попадает в общий парсер), а не молча обрабатывается как текст.

## 4. Валидация при создании (found, `F2N.A01`)

Единый валидатор, общий для всех версионированных полей создания. Бросает исключение, код ошибки **11**, если не указано иное:

| Проверка | Правило | Строка ошибки |
|-------|------|--------------|
| Имя присутствует | бит `name` должен быть установлен | `poll_creation_missing_name` |
| Длина имени | 1–5000 символов (если только мягкий контекст парсинга не обходит это, §4.1) | `poll_creation_invalid_name` |
| Правильный ответ викторины | если `pollType=QUIZ`, бит `correctAnswer` должен быть установлен | `poll_creation_missing_correct_answer` |
| Варианты присутствуют | хотя бы один вариант, если не применяется обход нулевого числа вариантов (§4.1) | `poll_creation_missing_options` |
| Число вариантов (нижняя граница) | ≥ 2 варианта (0 при обходе) | `poll_creation_invalid_options_count` |
| Число вариантов (верхняя граница) | ≤ `min(AB int 1408, 12)` — 12 — это жёсткий потолок клиента независимо от значения с сервера | `poll_creation_invalid_options_count` |
| Длина имени варианта | 1–2500 символов на вариант | `poll_creation_invalid_option` |
| Имя правильного ответа | для викторины `correctAnswer.optionName` не должно быть пустым | `poll_creation_missing_correct_answer_name` |
| Дублирующиеся варианты | имена вариантов должны быть уникальны | `poll_creation_duplicate_options` |
| Дублирующиеся варианты после обрезки пробелов | под флагом AB **25758** имена, обрезанные по пробелам, также должны быть уникальны | `poll_creation_duplicate_trimmed_options` |
| Правильный ответ совпадает с вариантом | имя правильного ответа викторины должно совпадать с именем одного из вариантов | `poll_creation_unmatched_correct_answer` |
| Присутствие предела выбора | бит `selectableOptionsCount` должен быть установлен | `poll_creation_missing_selectable_options_count` |
| Диапазон предела выбора | `0 <= selectableOptionsCount <= options.size()` (или `<= min(1408,12)` при обходе) | `poll_creation_invalid_selectable_options_count` |

### 4.1 Обход с нулём вариантов / мягкий обход (найденный путь кода, семантика — inferred)

Локальный булев флаг (`z`), вычисляемый из AB bool **37909**, учитывается только когда внутренний счётчик контекста парсинга равен 1; он смягчает минимальное число вариантов до 0 и расширяет потолок предела выбора до чистой границы `min(1408,12)` вместо `options.size()`. Значение контекста парсинга, которому это соответствует (обычный приём против какого-то другого пути поступления, например синхронизации истории), не установлено; это фиксируется как found-но-необъяснённое, а не как подтверждённая пользовательская функция «опрос без вариантов».

### 4.2 Обход синхронизации истории / мягкого имени

Отдельный контекстный флаг (`c33371Eg0.A0W`) обходит и проверку длины имени, и (аналогично, в `F39`, §9) проверку длины имени снимка результатов, принимая исходную строку без проверки. Согласуется с путём парсинга из доверенного источника (например, локальным повторным импортом истории), а не с обычным сетевым приёмом; независимо не подтверждено.

## 5. Варианты опроса с изображениями: `pollCreationOptionImageMessage`

### 5.1 Структура и связывание (found)

`pollCreationOptionImageMessage` (поле 90) оборачивает обычное загруженное `ImageMessage` внутри `FutureProofMessage` — изображение **не** встроено в `PollCreationMessage.Option`. Каждое изображение варианта отправляется как собственное дочернее сообщение, связанное с (ещё не отправленным) опросом через `MessageContextInfo.messageAssociation`, тип связи `MEDIA_POLL = 6` (`AnonymousClass122.MEDIA_POLL`; значение enum в этой сборке — в предыдущей сборке оно было 7, числовое значение нестабильно между версиями и должно перечитываться в каждом релизе). Вспомогательный класс отправки «MediaPollAssociationProvider» (в `C20M`) считает строки `message_association` для row id родительского опроса и типа связи `6`; когда счёт достигает числа вариантов, все изображения вариантов считаются загруженными, и клиент переходит к отправке самого опроса с `pollContentType = IMAGE`.

### 5.2 Хеш варианта для вариантов с изображением (inferred, перенесено из более ранней сборки, не выведено построчно заново в 2.26.41.6)

Для обычных текстовых вариантов проводное поле `optionHash` оставляется пустым; единственный хеш, вычисляемый для текстового варианта, — это локальный дайджест для поиска `C13J.A00`:

```text
optionHash(text option) = Base64(SHA-256(UTF8(optionName)))
```

(подтверждено непосредственно в 2.26.41.6, §9.1 — это хеш, используемый для сопоставления выбранных вариантов в голосе, а не proto-поле `optionHash`). Для вариантов **с изображением** заполняется proto-поле `optionHash`; трассировка последовательности отправки в предыдущей версии показала, что оно комбинирует хеш имени варианта с `fileSha256` загруженного изображения:

```text
nameHash   = lowerHex(SHA-256(UTF8(optionName)))
imageHash  = base64(imageMessage.fileSha256)
optionHash = lowerHex(SHA-256(UTF8(nameHash + imageHash)))
```

Эта формула не была повторно проверена по коду 2.26.41.6 в этом анализе (вычисляющий класс не был найден); она переносится как inferred и должна быть перепроверена перед тем, как на неё опираться.

## 6. `pollAddOptionMessage` (`C30556DRc`, поле 121)

### 6.1 Поля (found)

`pollCreationMessageKey` **1** (`MessageKey`), `addOption` **2** (`PollCreationMessage.Option`), `metadata` **3** (`PollUpdateMessageMetadata`, та же форма, что у голоса, §7).

### 6.2 Отправка (found, `F2L.ADr`)

Строит один `Option` из нового имени (и, для опросов с изображениями, его хеша), прикрепляет ключ исходного опроса и — для чатов 1:1, не в контексте правки — разрешает идентичность отправителя через границу LID/PN так же, как это делает слой message-secret для других add-on'ов (см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §6.1, шаг 4). Сам вариант *не* шифруется как secret на этом слое так, как это делает `pollUpdateMessage`: payload добавления варианта передаётся как обычное поле сообщения; то, что оборачивается в `secretEncryptedMessage` (тип `POLL_ADD_OPTION`), — это попытка добавления варианта целиком, когда она должна идти по схеме message-secret (§8).

### 6.3 Валидация при приёме (found, `F2L.CM7`)

| Проверка | Ошибка |
|-------|-------|
| Флаг функции: AB int **25758** должен быть ненулевым | ошибка **10017** |
| `pollCreationMessageKey` присутствует | `poll_add_option_missing_poll_message_key` |
| `addOption` присутствует | `poll_add_option_missing_poll_option` |
| Имя варианта не пустое, ≤ 2500 символов | `poll_add_option_invalid_option` |

Полученный локальный объект шифруется как secret для передачи с use case `Poll Add Option` (подтверждённый вызов вспомогательной функции message-secret с `AnonymousClass122.POLL_ADD_OPTION` как тегом связи). Добавленные варианты отслеживаются для сопоставления с существующими вариантами так же, как и варианты с изображениями (тип связи `POLL_ADD_OPTION = 18`).

## 7. `pollUpdateMessage` (голос и метаданные голоса)

Полная криптография (HKDF use case `Poll Vote`, AAD, AES-GCM, повтор идентичности LID/PN) описана в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §3–§7; этот раздел охватывает только то, что обработчик голоса в опросе (`DUA`, расширяет `F2P`) делает с открытым текстом.

### 7.1 Два пути отправки/приёма (found)

AB bool **6772** выбирает между:
- **включено** (текущее): общий вспомогательный класс шифрования (`C33285Eeb`) строит шифротекст и `MessageKey`; при наличии ранее сохранённой пары `(iv, payload)` голос повторяется из неё вместо повторного шифрования.
- **выключено** (устаревшее): встроенная ветка в `DUA` делает тот же вызов HKDF/AES-GCM напрямую, сама выводя целевую идентичность отправителя (собственный LID для голосов за собственный опрос голосующего, иначе — разрешённый JID цели голоса).

### 7.2 Payload голоса: `PollVoteMessage` (`DPF`)

Единственное поле `selectedOptions` **1**, repeated bytes — каждая запись — это 32-байтовый SHA-256-дайджест имени варианта (§9.1), а не индекс. `MessageAddOnPollVoteUtils` (`AbstractC33199EdC`) валидирует расшифрованный выбор:

| Проверка | Правило | Тег лога |
|-------|------|---------|
| Размер выбора | ≤ 12 **и** ≤ `selectableOptionsCount` опроса (если > 0) | `poll_vote_invalid_options_count` |
| Форма хеша | каждый выбранный хеш декодируется ровно в 32 байта | `poll_vote_invalid_option_hashes` |
| Дубликаты | в одном голосе не должно быть повторяющихся хешей | `poll_vote_duplicate_option_hashes` |
| Разрешение | каждый выбранный хеш должен совпадать с одним из известных (неудалённых) хешей вариантов опроса | возвращает результат с ошибкой, нет совпадения -> голос отклоняется |

### 7.3 Время окончания и метаданные (found, `DUA.A01`)

Голос, чей `senderTimestampMs` позже `endTime` опроса, отклоняется (`poll_update_past_end_time`); под AB bool **2321** событие отклонённого голоса дополнительно питает телеметрический счётчик (`N0e`). `metadata` голоса (`pollNameHash`, `lastEditStanzaId`) ставится при отправке только под AB bool **31593**; при приёме отсутствующий/пустой блок метаданных логируется как `"unstamped"` (сам по себе не отклоняется), тогда как *несовпадающая* метка (проверяется `C32977EZa`) отбрасывает голос с `poll_update_tc_drop`. Эти метаданные существуют, чтобы клиент мог обнаружить, что голосует против опроса, чью историю правок он ещё не догнал.

## 8. Правка опроса (`secretEncryptedMessage`, `secretEncType = POLL_EDIT`)

Передаётся внутри обычной обёртки `secretEncryptedMessage` (поле 82), а не специфичного для опросов носителя; см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §5/§7.4 про конверт, AAD и таблицу кодов ошибок (`poll_edit_message_stanza_invalid`, флаг AB int **24886**, ошибка **10016**). Специфичная для опросов валидация (`F3Y`, `SecretEncryptedMessageDeserializationValidator`) требует:

- внутреннее сообщение имеет тип FMessage 66 и является опросом как до, так и после правки;
- `endTime`, `hideParticipantName`, `allowAddOption`, `selectableOptionsCount` и `pollType` **не изменяются** между сохранённым опросом и отредактированным — различаться может только текст вопроса и/или текст вариантов;
- сопоставление вариантов: при включённом флаге на уровне чата (`EOI.A01()`, id не установлен) отредактированные варианты сопоставляются с сохранённой историей переименований через последовательное (сохраняющее порядок) сопоставление, позволяя переименовывать варианты на месте; точное поведение ветки сравнения без переименования — inferred (JADX снова теряет часть потока управления — в декомпилированной форме функция в этой ветке проваливается в `poll_edit_invalid_edits`, что вряд ли является реальным поведением клиента для правки без изменений).

В ресурсах существует строка тоста `"Couldn't edit poll"`, подтверждающая, что правка опроса видна пользователю в этой сборке, а не является просто зарезервированным путём протокола.

## 9. Внутреннее устройство сопоставления голосов

### 9.1 Хеш варианта (found, `C13J.A00`)

```text
optionHash = Base64(SHA-256(UTF8(optionName)))
```

Обычный SHA-256 от видимого текста варианта, без ключевого материала. Это значение хранится для каждого локального варианта (`C33283EeZ.A02`) и значение, с которым сопоставляются записи `selectedOptions` голоса. Любое приложение, знающее текст варианта, может вычислить тот же хеш — приватность голоса целиком обеспечивается шифрованием payload'а голоса на уровне message-secret (§7 и [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md)), а не тем, что хеш невозможно угадать.

## 10. Модель приватности/анонимности голоса

| Утверждение | Статус |
|-------|--------|
| Голоса шифруются end-to-end для каждого голосующего и каждого опроса (HKDF use case `Poll Vote`) | found, [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §3 |
| Выбранный вариант идентифицируется хешем содержимого, а не индексом | found, §9.1 |
| `hideParticipantName` («Hide voter names» / «Скрыть имена проголосовавших») подавляет отображение того, кто проголосовал, в UI | found (строка `str2137`, поле 10 `PollCreationMessage`) |
| `hideParticipantName` скрывает голосующего от сервера или от других клиентов на уровне протокола | **не подтверждается прочитанным здесь кодом** — конвертные поля `participant`/`from` (т.е. идентичность голосующего) доставляются и аутентифицируются одинаково для любого add-on'а независимо от этого флага (см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §8); `hideParticipantName` — это настройка объекта опроса, влияющая только на отображение, а не изменение маршрутизации или шифрования |
| Создатель опроса всегда может определить, кто проголосовал | inferred — ничто в пути расшифровки голоса (§7, §9) не зависит от `hideParticipantName`; клиент создателя расшифровывает каждый голос с идентичностью голосующего в качестве модификатора |

Короче говоря: опросы WhatsApp не анонимны для создателя опроса. «Hide voter names» / «Скрыть имена проголосовавших» контролирует только то, видят ли *другие участники* (в списке «Голоса в опросе»), кто проголосовал; это не меняет того, что криптографически связано с голосом, а сервер в любом случае никогда не узнаёт содержимое голоса (обычная гарантия E2E, не что-то специфичное для этого флага).

## 11. Множественный выбор против одиночного

`selectableOptionsCount` (поле 4) — единственный механизм: голос с большим числом выборов, чем это значение, отклоняется (§7.2). На проводе нет отдельного булева «is multi-select» — одиночный выбор — это просто `selectableOptionsCount = 1`. UI создания представляет это как единственный переключатель, **«Allow multiple answers» / «Разрешить несколько ответов»** (строка `str425f`); предполагается (inferred), что при выключенном состоянии клиент отправляет `selectableOptionsCount = 1`, а при включённом — `selectableOptionsCount = options.size()` (похоже, UI не предоставляет произвольный числовой предел — выведено из единственной булевой строки, не подтверждено независимо в коде UI создания). Сам протокол допускает любое значение `0..options.size()` (§4), так что значение на стороне клиента, отличное от 1 или «все варианты», возможно, даже если стандартный UI его не предлагает. Викторины неявно одиночного выбора (один правильный ответ; строка для голосующего `"Quiz • Select one correct answer"`, `str57a5`).

Подписи, видимые голосующему, подтверждают два режима: `"Select one"` (`str3865`) против `"Select one or more"` (`str3866`).

## 12. `pollResultSnapshotMessage` / `V3`: снимок на момент пересылки

### 12.1 Назначение (found, `F1A`)

Пересылка живого опроса в другой чат **не** пересылает интерактивный опрос. `F1A` (один из нескольких конвертеров «forward», все реализующие один и тот же интерфейс конвертации, используемый для разных типов сообщений — конвертер-сосед для неподдерживаемых типов бросает `"Cannot forward message of type: ..."`) преобразует живой опрос (`C13J`) в объект `Dd2`: текст вопроса, имя каждого варианта и **текущее локальное число голосов**, а также тип опрос/викторина. Это затем сериализуется как `pollResultSnapshotMessage` (обычный опрос) или `pollResultSnapshotMessageV3` (викторина) и отображается отдельным view holder'ом (`DWH`), отличным от пузыря интерактивного опроса.

### 12.2 Поля (found, `DSF`)

`name` **1** (string), `pollVotes` **2** (repeated `PollVote` — `optionName` **1**, `optionVoteCount` **2**), `contextInfo` **3**, `pollType` **4** (тот же enum `PollType`, что и при создании).

### 12.3 Валидация (found, `F39`)

Та же форма проверок, что и при создании: имя 1–5000 символов, не менее 2 вариантов, не более `min(AB 1408, 12)` вариантов, имя каждого варианта 1–2500 символов. Для варианта **викторины** (`V3`) счётчики голосов принудительно устанавливаются в 0 при отправке — пересланный снимок викторины никогда не раскрывает подсчёты, только вопрос и список вариантов.

## 15. Baileys (только подтверждённые факты)

[WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §17 уже охватывает те части JavaScript-реализации (`baron-baileys-v2` 1.5.17), которые относятся к опросам, на основе чтения `src/Utils/process-message.js`, `src/Utils/reporting-utils.js`, `src/Utils/messages.js`, `src/Socket/messages-send.js`:

- Вывод HKDF и строки use case'ов `Poll Vote`, `Event Response`, `Enc Comment`, `Enc Reaction`, `Event Edit`, `Message Edit`, `Poll Edit`, `Poll Add Option` точно совпадают с литералами Android-клиента, включая AAD `id\0modifier` для `Poll Vote`.
- AAD, повтор идентичности (PN/LID) и обработка отсутствующего secret'а (откат к необработанному, нерасшифрованному обновлению) совпадают с поведением Android, описанным в этом отчёте (§7) и в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §7.2–§7.3.
- Путь шифрования на стороне отправки для `pollUpdateMessage` (или `encReactionMessage`, `encEventResponseMessage`, `encCommentMessage`) в прочитанных файлах не найден — то есть эта реализация могла расшифровать входящий голос, но в просмотренных файлах не было кода для шифрования и отправки такого голоса.

Ничто специфичное для опросов сверх уже сказанного там не было независимо перепроверено в этом анализе (код Baileys для создания опроса, хеша варианта или правки опроса не читался); дальнейших утверждений про Baileys здесь не делается.

## 16. Случаи ошибок

| Симптом | Причина | Решение |
|---------|-------|-----|
| `poll_creation_invalid_options_count` | меньше 2 или больше `min(1408,12)` вариантов | держать число вариантов в пределах диапазона |
| `poll_creation_unmatched_correct_answer` | `correctAnswer.optionName` викторины не совпадает ни с одним именем варианта | задать правильный ответ, точно совпадающий с вариантом |
| Опрос молча не показывается (понижение версии) | `endTime`/`hideParticipantName`/`allowAddOption` установлены на опросе V6, но соответствующий флаг AB выключен у получателя | на стороне отправителя, не исправляется содержимым; ограничение возможностей получателя |
| `poll_vote_invalid_options_count` | голос выбирает больше вариантов, чем `selectableOptionsCount`, или больше 12 | соблюдать предел опроса |
| `poll_update_past_end_time` | временная метка голоса (или добавления варианта / правки) позже `endTime` | голосовать до закрытия опроса |
| `poll_update_tc_drop` | `pollNameHash`/`lastEditStanzaId` голоса не совпадает с представлением получателя об опросе | синхронизировать историю правок опроса перед голосованием |
| ошибка **10017** при добавлении варианта | AB **25758** равен нулю у получателя | ограничение возможностей получателя |
| ошибка **10016** при правке опроса | AB **24886** равен нулю у получателя | ограничение возможностей получателя |
| `poll_add_option_past_end_time` | вариант добавлен после `endTime` | добавлять варианты до закрытия опроса |

## 17. Ключевые отличия

| Это | Не это |
|------|----------|
| `pollCreationMessage`/V2/V3/V5/V6 (тип `PollCreationMessage`) | `pollCreationMessageV4` (`FutureProofMessage`, оборачивающий внутренний базовый опрос) |

## 18. Полный поток (создание, вариант с изображением, голос, пересылка)

```
[Creator]                                          [Server]                     [Participant]
   │ build PollCreationMessage                        │                              │
   │  (quiz? -> V5; community subgroup? -> V2;         │                              │
   │   extras(endTime/hide/addOpt)? -> V6; else V3)    │                              │
   │ [image poll]                                      │                              │
   │  send N × pollCreationOptionImageMessage           │                              │
   │   (messageAssociation MEDIA_POLL=6, parent key)───▶───────────────────────────▶ received,
   │  wait for all fileSha256                           │                              associated
   │  compute optionHash per option                     │                              │
   │ send pollCreationMessage* ─────────────────────────▶──────────────────────────▶ store poll,
   │                                                    │                              secret
   │                                                    │        select option(s)     │
   │                                                    │        hash = SHA256(name)  │
   │                                                    │        key = HKDF(secret,   │
   │                                                    │          pollId‖creator‖    │
   │                                                    │          voter‖"Poll Vote") │
   │                                                    │        pollUpdateMessage    │
   │◀────────────────────────────────────────────────────◀ {key, vote{ct,iv}, ts} ────│
   │ validate: end time, selection count/hash shape     │                              │
   │ decrypt, resolve hash -> known option              │                              │
   │ apply vote                                         │                              │
   │                                                    │                              │
   │ [user forwards the poll elsewhere]                 │                              │
   │ convert live poll -> Dd2 (name, per-option count)  │                              │
   │ quiz? zero the counts                              │                              │
   │ send pollResultSnapshotMessage[/V3] ───────────────▶──────────────────────────▶ static bubble,
   │                                                    │                              not interactive
```
