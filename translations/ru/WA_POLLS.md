# WhatsApp Опросы — Full RE Report
**Версия:** 2.26.41.6 | **Дата:** 2026-11-01
**Область:** семейство сообщений опросов (`pollCreationMessage` до `pollCreationMessageV6`, `pollCreationOptionImageMessage`, `pollAddOptionMessage`, `pollUpdateMessage`, `pollResultSnapshotMessage`/`V3`), история версий и логика выбора при отправке/получении, валидация создания и лимиты, связывание изображения варианта опроса, модель выбора голоса и приватности, множественный выбор vs одиночный, редактирование опроса, снапшот результата на момент пересылки, флаги функций

---

## 1. Что это

Опрос — это под-объект `Message` (`PollCreationMessage`, многократно переиспользуемый без изменений в шести версионированных полях верхнего уровня), несущий вопрос, список вариантов, лимит выбора и опциональные настройки квиза/времени окончания/видимости. Голоса (`pollUpdateMessage`), добавленные варианты (`pollAddOptionMessage`) и правки (`secretEncryptedMessage`) — отдельные последующие сообщения, привязанные к id создающего сообщения и ключуемые его посообщенческим секретом; это шифрование (случаи использования HKDF, AES-GCM, AAD, повтор идентичности) описано в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) и здесь не повторяется. Этот отчёт охватывает слой типов сообщений: какое поле несёт что, как клиент выбирает между ними, валидацию и лимиты, и что делают обработчики, специфичные для опросов, с расшифрованными полезными нагрузками. Все находки — статический анализ декомпилированного APK 2.26.41.6 (исходники Java в `java_src/`, плюс `res/values/strings.xml`); ничего не было захвачено по протоколу. Уровни: **found** = прочитано в коде/ресурсах, **inferred** = выведено из кода, **unknown** = не разрешено.

### 2.2 Локальное представление

Клиент хранит разобранный опрос как `C13J` (вариант квиза с изображением — `C13K`), с вариантами как объектами `C33283EeZ`, несущими исходное имя (`A04`), локально вычисленный дайджест SHA-256 имени (`A02`, §9.1) и, для вариантов с изображением, протокольный `optionHash` (`A08`).

## 3. История версий

### 3.1 Какое поле используется при отправке (found, `F2N.A00`/`A02`)

```text
pollType == QUIZ (correct answer set)              -> pollCreationMessageV5
chat is a community default-subgroup (group_type 3) -> pollCreationMessageV2
else:
  hideParticipantName / endTime / allowAddOption set -> pollCreationMessageV6
  none of those set                                   -> pollCreationMessageV3
```

`pollCreationMessageV4` никогда не заполняется путём отправки, прочитанным в этом проходе; он появляется только при получении (§3.3). Проверка на сообщество повторно использует тот же предикат `group_type == 3`, что и резервный путь нешифрованной реакции в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §6.2 (`C0GQ.A0A(chat) == 3`, задаётся из `isDefaultSubgroup_`); почему опрос подгруппы по умолчанию получает собственный версионированный слот вместо V3/V6, прочитанный здесь код не объясняет (предположение: исторический порядок внедрения, поскольку номер поля V2 самый низкий в расширенном наборе).

Так что на практике: **V3** — текущий слот для обычного опроса с множественным/одиночным выбором без дополнений, **V6** — текущий для опроса с временем окончания, скрытыми именами голосующих или разрешением добавления вариантов, **V5** — текущий для квизов, а **V2** — специфичный для подгруппы сообщества вариант той же базовой формы. **V1** (неверсионированное поле 49) и **V4** не выбираются отправителем в этой сборке.

### 3.2 `pollCreationMessageV4` = обёртка обратной совместимости (found, `F2N.CM7`)

Тип proto у V4 — `FutureProofMessage` (`BD2`, единственное поле `message` = внутренний `Message`). При получении, когда заполнен слот V4, клиент разворачивает `BD2.message_` и читает поле `pollCreationMessage` (49) *этого* внутреннего сообщения как фактический `PollCreationMessage`. Это настоящий резервный конверт, а не мёртвое поле: отправитель, которому нужно отправить более новый/неопределённый вариант опроса, может обернуть базовый опрос (в форме поля 49) внутри V4, так что более старые клиенты — которые понимают только обычное разворачивание `FutureProofMessage`, а не более новый слот — всё равно отрендерят обычный опрос. Ни один путь кода в этом проходе не заполняет V4 при отправке, так что это существует для прямой/обратной совместимости между версиями клиента, а не для чего-либо, что сам клиент 2.26.41.6 отправляет (предположение).

### 3.3 Выбор на стороне получения и понижение версии (found, приблизительно; декомпилятор потерял часть структуры ветвления)

`F2N.CM7` проверяет битовые поля `Message` в порядке V1 → V2 → V4 → V5 → V6 → резерв-V3 и разбирает то версионированное поле, которое заполнено, в тот же валидатор (`F2N.A01`, §4). Три флага ограничивают принятие дополнительных полей V6 при получении; когда флаг выключен, опрос **понижается в версии** (разбирается как обычный заглушка future-proof, а не как пузырь опроса), а не отклоняется полностью:

| Дополнительное поле | Ограничение | Эффект, когда флаг выключен |
|-------------|------|--------------------------|
| `endTime` | AB int **24884** (`receivingEnabled`) | логируется `poll downgraded to FMessageFuture (receiving disabled)`, не рендерится как опрос |
| `hideParticipantName` | AB int **24885** | понижение версии (точная полярность проверки не полностью разрешена из декомпилированного потока управления) |
| `allowAddOption` | AB int **25758** | понижение версии |

Точную вложенность этих трёх условий не удалось полностью восстановить (JADX сообщает о дублированных/недостижимых блоках в `F2N.CM7`); сами флаги ограничения и результат понижения версии — found, точная булева комбинация — inferred.

### 3.4 Ограничение по содержимому-изображению

`pollContentType = IMAGE` учитывается только на пути разбора V3/V5, когда установлен бит для `pollContentType`; если он установлен, но значение не `IMAGE`, сообщение отклоняется (`return null`, переходит к общему парсеру), а не молча обрабатывается как текст.

## 4. Валидация создания (found, `F2N.A01`)

Единый валидатор, общий для всех версионированных полей создания. Бросает исключение с кодом ошибки **11**, если не указано иное:

| Проверка | Правило | Строка ошибки |
|-------|------|--------------|
| Наличие имени | бит `name` должен быть установлен | `poll_creation_missing_name` |
| Длина имени | 1–5000 символов (если лимит не обходится в снисходительном контексте разбора, §4.1) | `poll_creation_invalid_name` |
| Правильный ответ квиза | если `pollType=QUIZ`, бит `correctAnswer` должен быть установлен | `poll_creation_missing_correct_answer` |
| Наличие вариантов | хотя бы один вариант, если не применяется обход нулевого числа вариантов (§4.1) | `poll_creation_missing_options` |
| Количество вариантов (нижняя граница) | ≥ 2 варианта (0 при обходе) | `poll_creation_invalid_options_count` |
| Количество вариантов (верхняя граница) | ≤ `min(AB int 1408, 12)` — 12 — жёсткий предел клиента независимо от серверного значения | `poll_creation_invalid_options_count` |
| Длина имени варианта | 1–2500 символов на вариант | `poll_creation_invalid_option` |
| Имя правильного ответа | если квиз, `correctAnswer.optionName` должно быть непустым | `poll_creation_missing_correct_answer_name` |
| Дублирующиеся варианты | имена вариантов должны быть уникальны | `poll_creation_duplicate_options` |
| Дублирующиеся обрезанные варианты | под флагом AB **25758** имена с обрезанными пробелами также должны быть уникальны | `poll_creation_duplicate_trimmed_options` |
| Правильный ответ совпадает с вариантом | имя правильного ответа квиза должно совпадать с именем одного из вариантов | `poll_creation_unmatched_correct_answer` |
| Наличие числа выбираемых вариантов | бит `selectableOptionsCount` должен быть установлен | `poll_creation_missing_selectable_options_count` |
| Диапазон числа выбираемых вариантов | `0 <= selectableOptionsCount <= options.size()` (или `<= min(1408,12)` при обходе) | `poll_creation_invalid_selectable_options_count` |

### 4.1 Обход нулевого числа вариантов / снисходительный обход (путь кода найден, семантика предположена)

Локальное булево значение (`z`), вычисленное из AB bool **37909**, используемое только когда внутренний счётчик контекста разбора равен 1, ослабляет минимальное число вариантов до 0 и расширяет верхний предел числа выбираемых вариантов до сырой границы `min(1408,12)` вместо `options.size()`. Значение контекста разбора, которому это соответствует (обычное получение vs. некий другой путь поступления, например синхронизация истории), не разрешено; это зафиксировано как найденное-но-необъяснённое, а не как подтверждённая видимая пользователю функция "опрос без вариантов".

### 4.2 Обход истории-синхронизации / снисходительного имени

Отдельный флаг контекста (`c33371Eg0.A0W`) обходит и проверку длины имени, и (эквивалентно, в `F39`, §9) проверку длины имени в снапшоте результата, принимая сырую строку без проверки. Согласуется с путём разбора доверенного источника (например, локальный повторный импорт истории), а не с обычным сетевым получением; не подтверждено независимо.

## 5. Варианты опроса с изображениями: `pollCreationOptionImageMessage`

### 5.1 Структура и связывание (found)

`pollCreationOptionImageMessage` (поле 90) оборачивает обычное загруженное `ImageMessage` внутри `FutureProofMessage` — изображение **не** встроено в `PollCreationMessage.Option`. Каждое изображение варианта отправляется как собственное дочернее сообщение, связанное с (ещё не отправленным) опросом через `MessageContextInfo.messageAssociation`, тип связи `MEDIA_POLL = 6` (`AnonymousClass122.MEDIA_POLL`; значение enum этой сборки — в более ранней сборке оно было 7, числовое значение не стабильно между версиями и должно быть перепроверено для каждого релиза). Вспомогательный класс отправляющей стороны "MediaPollAssociationProvider" (в `C20M`) считает строки `message_association` для id строки родительского опроса и типа связи `6`; когда счётчик достигает числа вариантов, все изображения вариантов считаются загруженными, и клиент переходит к отправке самого опроса с `pollContentType = IMAGE`.

### 5.2 Хэш варианта для вариантов с изображением (inferred, перенесено из более ранней сборки, не выведено заново построчно в 2.26.41.6)

Для обычных текстовых вариантов протокольное поле `optionHash` оставляется пустым; единственный хэш, вычисляемый для текстового варианта — локальный хэш для поиска `C13J.A00`:

```text
optionHash(text option) = Base64(SHA-256(UTF8(optionName)))
```

(подтверждено непосредственно в 2.26.41.6, §9.1 — это хэш, используемый для сопоставления выбранных вариантов голоса, не протокольное поле `optionHash`). Для вариантов **с изображением** протокольное поле `optionHash` заполняется; трассировка последовательности отправки в более ранней версии обнаружила, что оно сочетает хэш имени варианта с `fileSha256` загруженного изображения:

```text
nameHash   = lowerHex(SHA-256(UTF8(optionName)))
imageHash  = base64(imageMessage.fileSha256)
optionHash = lowerHex(SHA-256(UTF8(nameHash + imageHash)))
```

Эта формула не была перепроверена по коду 2.26.41.6 в этом проходе (вычисляющий класс не был обнаружен); она переносится как предположение и должна быть перепроверена перед тем, как на неё опираться.

## 6. `pollAddOptionMessage` (`C30556DRc`, поле 121)

### 6.1 Поля (found)

`pollCreationMessageKey` **1** (`MessageKey`), `addOption` **2** (`PollCreationMessage.Option`), `metadata` **3** (`PollUpdateMessageMetadata`, та же форма, что у голоса, §7).

### 6.2 Отправка (found, `F2L.ADr`)

Строит один `Option` из нового имени (и, для опросов с изображениями, его хэша), прикрепляет ключ исходного опроса и — для чатов 1:1, когда не контекст редактирования — разрешает идентичность отправителя через границу LID/PN так же, как это делает слой секретов сообщения для других дополнений (см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §6.1 шаг 4). Сам вариант *не* зашифрован секретом на этом слое, как это делается для `pollUpdateMessage`: полезная нагрузка добавления варианта передаётся как обычное поле сообщения; то, что оборачивается в `secretEncryptedMessage` (тип `POLL_ADD_OPTION`) — это попытка добавления варианта в целом, когда она должна идти через схему секрета сообщения (§8).

### 6.3 Валидация при получении (found, `F2L.CM7`)

| Проверка | Ошибка |
|-------|-------|
| Ограничение функции: AB int **25758** должен быть не нулём | ошибка **10017** |
| Присутствует `pollCreationMessageKey` | `poll_add_option_missing_poll_message_key` |
| Присутствует `addOption` | `poll_add_option_missing_poll_option` |
| Имя варианта непусто, ≤ 2500 символов | `poll_add_option_invalid_option` |

Получившийся локальный объект шифруется секретом для передачи с использованием случая использования `Poll Add Option` (подтверждён вызов в помощник шифрования секрета сообщения с `AnonymousClass122.POLL_ADD_OPTION` как тегом связи). Добавленные варианты отслеживаются для сопоставления с существующими вариантами так же, как это делается для вариантов опроса с изображениями (тип связи `POLL_ADD_OPTION = 18`).

## 7. `pollUpdateMessage` (голос и метаданные голоса)

Полная криптография (случай использования HKDF `Poll Vote`, AAD, AES-GCM, повтор идентичности LID/PN) описана в [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §3–§7; этот раздел охватывает только то, что обработчик голоса в опросе (`DUA`, расширяет `F2P`) делает с открытым текстом.

### 7.1 Два пути отправки/получения (found)

AB bool **6772** выбирает между:
- **включено** (текущий вариант): общий помощник шифрования (`C33285Eeb`) строит шифротекст и `MessageKey`; голос повторно отправляется из ранее сохранённой пары `(iv, payload)`, когда она присутствует, вместо повторного шифрования.
- **выключено** (устаревший вариант): встроенная ветка в `DUA` делает тот же вызов HKDF/AES-GCM напрямую, самостоятельно выводя целевую идентичность отправителя (собственный LID для голосов за собственный опрос голосующего, иначе разрешённый JID цели голоса).

### 7.2 Полезная нагрузка голоса: `PollVoteMessage` (`DPF`)

Единственное поле `selectedOptions` **1**, повторяемые bytes — каждая запись — это 32-байтный дайджест SHA-256 имени варианта (§9.1), не индекс. `MessageAddOnPollVoteUtils` (`AbstractC33199EdC`) проверяет расшифрованный выбор:

| Проверка | Правило | Тег лога |
|-------|------|---------|
| Размер выбора | ≤ 12 **и** ≤ `selectableOptionsCount` опроса (когда > 0) | `poll_vote_invalid_options_count` |
| Форма хэша | каждый выбранный хэш декодируется ровно в 32 байта | `poll_vote_invalid_option_hashes` |
| Дубликаты | в одном голосе нет повторяющегося хэша | `poll_vote_duplicate_option_hashes` |
| Разрешение | каждый выбранный хэш должен совпадать с одним из известных (неудалённых) хэшей вариантов опроса | возвращает результат с ошибкой, нет совпадения -> голос отклонён |

### 7.3 Время окончания и метаданные (found, `DUA.A01`)

Голос, чей `senderTimestampMs` после `endTime` опроса, отклоняется (`poll_update_past_end_time`); под AB bool **2321** событие отклонённого голоса дополнительно питает телеметрический счётчик (`N0e`). Метаданные голоса `metadata` (`pollNameHash`, `lastEditStanzaId`) ставятся при отправке только под AB bool **31593**; при получении отсутствующий/пустой блок метаданных логируется как `"unstamped"` (сам по себе не отклоняется), в то время как *несовпадающая* отметка (проверяется `C32977EZa`) отбрасывает голос с `poll_update_tc_drop`. Эти метаданные существуют, чтобы клиент мог обнаружить, что он голосует за опрос, историю правок которого он ещё не догнал.

## 8. Редактирование опроса (`secretEncryptedMessage`, `secretEncType = POLL_EDIT`)

Передаётся внутри обычной обёртки `secretEncryptedMessage` (поле 82), не специфичного для опроса носителя; см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §5/§7.4 про конверт, AAD и таблицу кодов ошибок (`poll_edit_message_stanza_invalid`, ограничение AB int **24886**, ошибка **10016**). Специфичная для опросов валидация (`F3Y`, `SecretEncryptedMessageDeserializationValidator`) требует:

- внутреннее сообщение имеет FMessage-тип 66 и является опросом как до, так и после правки;
- `endTime`, `hideParticipantName`, `allowAddOption`, `selectableOptionsCount` и `pollType` **не изменены** между сохранённым опросом и отредактированным — может отличаться только текст вопроса и/или текст вариантов;
- сопоставление вариантов: при включённом флаге на чат (`EOI.A01()`, id не разрешён), отредактированные варианты сопоставляются с сохранённой историей переименований через последовательное (сохраняющее порядок) сопоставление, позволяя переименовывать варианты на месте; точное поведение ветки сравнения без переименования предположено (JADX снова теряет часть потока управления — функция в декомпилированной форме всегда проваливается в `poll_edit_invalid_edits` в этой ветке, что едва ли является реальным поведением клиента для правки без изменений).

Строка toast "Couldn't edit poll" существует в ресурсах, подтверждая, что редактирование опросов видно пользователю в этой сборке, а не просто зарезервированный путь протокола.

### 8.1 UI редактирования опроса (новое в 2.26.45.10) — операция протокола не разрешена

вспомогательные диалоги (`PollEditDiscardChangesDialog`, `PollEditSendFailedDialog`,

## 9. Внутреннее устройство сопоставления голосов

### 9.1 Хэш варианта (found, `C13J.A00`)

```text
optionHash = Base64(SHA-256(UTF8(optionName)))
```

Обычный SHA-256 видимого текста варианта, без ключевого материала. Это значение, хранящееся для каждого локального варианта (`C33283EeZ.A02`), и значение, с которым сопоставляются записи `selectedOptions` голоса. Любое приложение, знающее текст варианта, может вычислить тот же хэш — приватность голоса обеспечивается целиком шифрованием секретом сообщения полезной нагрузки голоса (§7, и [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md)), а не тем, что хэш невозможно угадать.

## 10. Модель приватности / анонимности голоса

| Утверждение | Статус |
|-------|-------|
| Голоса сквозно зашифрованы для каждого голосующего, для каждого опроса (случай использования HKDF `Poll Vote`) | found, [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §3 |
| Выбранный вариант идентифицируется хэшем содержимого, не индексом | found, §9.1 |
| `hideParticipantName` ("Скрыть имена проголосовавших") подавляет отображение того, кто проголосовал, в UI | found (строка `str2137`, поле 10 `PollCreationMessage`) |
| `hideParticipantName` скрывает голосующего от сервера или от других клиентов на уровне протокола | **не подтверждается прочитанным здесь кодом** — конверт `participant`/`from` (т.е. идентичность голосующего) доставляется и аутентифицируется одинаково для каждого дополнения независимо от этого флага (см. [WA_MESSAGE_SECRETS.md](./WA_MESSAGE_SECRETS.md) §8); `hideParticipantName` — настройка только отображения на объекте опроса, не изменение маршрутизации или шифрования |
| Создатель опроса всегда может определить, кто проголосовал | inferred — ничто в пути расшифровки голоса (§7, §9) не зависит от `hideParticipantName`; клиент создателя расшифровывает каждый голос с идентичностью голосующего как модификатором |

Короче: опросы WhatsApp не анонимны для создателя опроса. "Скрыть имена проголосовавших" контролирует только, видят ли *другие участники* (в списке "Голоса опроса"), кто проголосовал; это не меняет того, что криптографически привязано к голосу, и сервер в любом случае никогда не узнаёт содержимое голоса (обычная гарантия E2E, не что-то специфичное для этого флага).

## 11. Множественный выбор vs одиночный выбор

`selectableOptionsCount` (поле 4) — единственный механизм: голос с большим числом выборов, чем это значение, отклоняется (§7.2). На проводе нет отдельного булева значения "это множественный выбор" — одиночный выбор — это просто `selectableOptionsCount = 1`. UI создания представляет это как единый переключатель **"Разрешить несколько ответов"** (строка `str425f`); когда выключен, предполагается, что клиент отправляет `selectableOptionsCount = 1`, когда включён — предполагается, что клиент отправляет `selectableOptionsCount = options.size()` (похоже, UI не предоставляет произвольный числовой предел — предположено из единственной строки булева переключателя, не подтверждено независимо в коде UI создания). Сам протокол разрешает любое значение `0..options.size()` (§4), так что значение на стороне клиента, отличное от 1 или "все варианты", возможно, даже если стандартный UI его не предлагает. Квизы неявно одиночного выбора (один правильный ответ; строка, видимая голосующему, "Quiz • Select one correct answer", `str57a5`).

Метки, видимые голосующему, подтверждают два режима: `"Select one"` (`str3865`) vs. `"Select one or more"` (`str3866`).

## 12. `pollResultSnapshotMessage` / `V3`: снапшот на момент пересылки

### 12.1 Назначение (found, `F1A`)

Пересылка живого опроса в другой чат **не** пересылает интерактивный опрос. `F1A` (один из нескольких конвертеров "forward", все реализующие общий интерфейс преобразования, используемый для разных типов сообщений — конвертер-сосед для неподдерживаемых типов бросает `"Cannot forward message of type: ..."`) преобразует живой опрос (`C13J`) в объект `Dd2`: текст вопроса, имя каждого варианта и **текущий локальный счётчик голосов**, а также тип опроса/квиза. Это затем сериализуется как `pollResultSnapshotMessage` (обычный опрос) или `pollResultSnapshotMessageV3` (квиз) и рендерится специальным держателем представления (`DWH`), отличным от пузыря интерактивного опроса.

### 12.2 Поля (found, `DSF`)

`name` **1** (string), `pollVotes` **2** (repeated `PollVote` — `optionName` **1**, `optionVoteCount` **2**), `contextInfo` **3**, `pollType` **4** (тот же enum `PollType`, что и при создании).

### 12.3 Валидация (found, `F39`)

Та же форма проверок, что и при создании: имя 1–5000 символов, минимум 2 варианта, максимум `min(AB 1408, 12)` вариантов, имя каждого варианта 1–2500 символов. Для варианта **квиза** (`V3`) счётчики голосов принудительно сбрасываются в 0 при отправке — пересланный снапшот квиза никогда не раскрывает подсчёты, только вопрос и список вариантов.

## 16. Случаи ошибок

| Симптом | Причина | Исправление |
|---------|-------|-----|
| `poll_creation_invalid_options_count` | меньше 2 или больше `min(1408,12)` вариантов | держать количество вариантов в пределах диапазона |

| ошибка **10016** при правке опроса | AB **24886** равен нулю у получателя | пробел в возможностях получателя |
| `poll_add_option_past_end_time` | вариант добавлен после `endTime` | добавлять варианты до закрытия опроса |

## 17. Ключевые различия

| Это | Не это |
|------|----------|
| `pollCreationMessage`/V2/V3/V5/V6 (тип `PollCreationMessage`) | `pollCreationMessageV4` (`FutureProofMessage`, оборачивающий внутренний базовый опрос) |
| `pollUpdateMessage` (голос, или метаданные голоса) | `secretEncryptedMessage` с `secretEncType=POLL_EDIT`/`POLL_ADD_OPTION` (правка опроса / добавление варианта) |
| `pollAddOptionMessage` (полезная нагрузка нового варианта) | обёртка `secretEncryptedMessage`, несущая его по протоколу, когда привязана к секрету сообщения |
| `pollResultSnapshotMessage`/V3 (статичный, пересланный) | живой интерактивный опрос (`pollCreationMessage*`) |
| Выбор варианта по хэшу SHA-256(имя) | выбор по индексу — опросы WhatsApp никогда не выбирают по позиции |
| `hideParticipantName` (настройка отображения UI) | анонимность отправителя голоса (не существует; создатель всегда разрешает идентичность голосующего) |
| `selectableOptionsCount` (единственный сигнал множественного/одиночного выбора) | отдельное булево значение "это множественный выбор" (не существует) |

## 18. Полный поток (создание, вариант с изображением, голос, пересылка)

```
[Creator]                                          [Server]                     [Participant]
   │ build PollCreationMessage                        │                              │
   │  (quiz? -> V5; community subgroup? -> V2;         │                              │
   │   extras(endTime/hide/addOpt)? -> V6; else V3)    │                              │
   │ [image poll]                                      │                              │
   │  send N × pollCreationOptionImageMessage           │                              │
   │   (messageAssociation MEDIA_POLL=6, parent key)───▶───────────────────────────▶ received,
   │  wait for all fileSha256                           │                              associated
   │  compute optionHash per option                     │                              │
   │ send pollCreationMessage* ─────────────────────────▶──────────────────────────▶ store poll,
   │                                                    │                              secret
   │                                                    │        select option(s)     │
   │                                                    │        hash = SHA256(name)  │
   │                                                    │        key = HKDF(secret,   │
   │                                                    │          pollId‖creator‖    │
   │                                                    │          voter‖"Poll Vote") │
   │                                                    │        pollUpdateMessage    │
   │◀────────────────────────────────────────────────────◀ {key, vote{ct,iv}, ts} ────│
   │ validate: end time, selection count/hash shape     │                              │
   │ decrypt, resolve hash -> known option              │                              │
```
